# Candle migration: implementation and performance report

Branch `candle` (SonicBoom) + `feat/onnx-supertonic-ops` (candle fork, on top of
`feat/audio-runtime`). Measured 2026-11-15. All numbers below come from the raw JSONL in
`benchmarks/results/2026-11-15-candle/` (tables regenerated by
`scripts/summarize_candle_bench.py`; the full machine-generated table is `SUMMARY.md`).

## 1. Bottom line

| Model | Current core | Candle (this branch) | Verdict |
|---|---|---|---|
| **Supertonic 3** | ORT CPU: RTF **0.28–0.41** | candle-onnx CPU **0.47–0.56**; Vulkan **0.72–0.84**; numerically equal to ORT | Works and is drop-in, but **slower** than ORT. No performance reason to switch. |
| **Qwen3-TTS** | GGUF 1.7B + llama.cpp Vulkan: RTF **2.3–2.8** (2026-10-16 measurement) | 1.7B on candle Vulkan BF16: RTF **4.96** (x-vector); 0.6B: **5.0** | Works, correct audio, about **2× slower** than the current backend. Pure Rust, single runtime, codec decode on the GPU. |
| **Kyutai TTS** | not available | candle Vulkan BF16: RTF **4.16**; CPU F32: **18.0** | **New capability** (no ORT/GGUF path exists). Correct speech; **not real time** on this hardware. |

Nothing here reaches real time (RTF < 1) except Supertonic, which already was. A full replacement
of ORT and llama.cpp is **not justified by these measurements**. What is justified:

* keep candle as an optional backend (all of it is behind cargo features, nothing default changes);
* use it for **Kyutai TTS**, which has no other path;
* revisit Qwen once the per-op overhead in the Vulkan backend is reduced (section 5).

Hardware: AMD BC-250 (RADV GFX1013, Vulkan 1.4, 2.64 + 5.28 GiB device heaps), 2 CPU cores,
15 GiB RAM, Rust 1.99, release builds, models loaded once, then warm runs.
RTF = wall time / audio seconds (lower is better; < 1 is faster than real time).

## 2. What was implemented

SonicBoom (`candle` branch, not committed per project rule):

* `src/tts/backend.rs` — `SupertonicBackend` trait; ORT implementation (the previous code, moved
  behind the trait) and candle-onnx implementation (`candle` / `candle-vulkan` features).
  `inference.rs`/`model.rs` call the trait; `ModelHandle::load_with(paths, BackendChoice)`.
* `vendor/qwen3-tts` — the previously removed Candle Qwen3-TTS crate (git history `98d59c8^`),
  ported to the fork's candle 0.11 and extended for Vulkan.
* `vendor/kyutai-tts` — **new** port of Kyutai DSM-TTS (`tts-1.6b-en_fr`) from the Python reference
  (LM, depformer with per-step weight schedule, demuxed text streams, speaker cross-attention,
  CFG-distilled conditioning, state machine, delayed codebooks) on top of vendored
  `vendor/moshi-core` (Mimi codec, Apache-2.0).
* `src/tts/providers/candle_models.rs` — `TtsProvider` implementations `qwen3-candle` and
  `kyutai-candle` (features `candle-qwen`, `candle-kyutai`) with the same lifecycle as the other
  native providers: hot-reloaded configuration, background load, `disabled / not_installed /
  loading / ready / error` status, registration in `ProviderPool`.
* **Self-contained build**: the fork's crates are vendored in `vendor/candle` (provenance and the
  local patch set in `vendor/candle/UPSTREAM.md`), so no sibling checkout is needed, and the candle
  features are part of the default feature set (Docker builds use `candle-qwen,candle-kyutai`).
* **Download manifests**: `qwen3-candle` (Qwen3-TTS 1.7B Base) and `kyutai-candle` (Kyutai TTS plus the
  `calm` voice) fetch pinned Hugging Face revisions with SHA-256/size verification through the
  existing asset downloader (atomic installs, verified-record reuse on restart, cancellation on
  config change, progress in `/api/providers`); `download = false` uses operator-managed files.
* **Studio / UI**: the Settings screen renders the new keys from the config schema (labels and
  descriptions translated in `en`/`es`); the Studio lists `qwen3-tts-candle` as a cloning model and
  `kyutai-tts-1.6b-en-fr` with its advertised voices (`capabilities[].voices`), and routes Kyutai
  jobs through `/api/tts/jobs?provider=kyutai-candle&voice=…`.
* **Server integration** (features `candle`, `candle-vulkan`, `candle-qwen`, `candle-kyutai`):
  config keys `model.backend` (`auto|ort|candle-cpu|candle-vulkan`, env `MODEL_BACKEND`, changing it
  reloads the model), `[providers.qwen3_candle]`, `[providers.kyutai_candle]` (schema, validation,
  loader keys, diffing); catalog models `qwen3-tts-candle` (voice profiles via
  `/api/voices/clones`) and `kyutai-tts-1.6b-en-fr` (named voices) on `/v1/audio/speech`;
  `/api/providers` reports the real engine and device. With a candle build, `backend = "auto"`
  resolves to candle, so candle **is** the engine of that build; ORT stays selectable.
* `vendor/kyutai-tts/src/spm.rs` — pure-Rust SentencePiece unigram encoder. The SentencePiece C++
  library bundles a static protobuf that collides with ONNX Runtime's (duplicate symbols at link
  time), so the two engines could not live in one binary. The Rust encoder is tested token-for-token
  against the C++ one on ~480 inputs (English, French, accents, CJK, emoji, URLs, random words).
* `examples/supertonic_backend_bench.rs`, `vendor/*/examples/*_bench.rs`, and
  `scripts/summarize_candle_bench.py`.

* **Parity** (identical seeded inputs through both engines, `supertonic-parity-*.jsonl`):
  duration equal (|Δ| = 0), denoise relative error ≤ 3.0e-6 after 5 steps, vocoder relative error

## 4. What the measurements say

1. **The big wins came from fixing the backend, not from the models.** Two changes dominate the
   whole project: depthwise conv (Supertonic 29× slower than ORT → 1.4–1.7×) and BF16 matmul on Vulkan
   (Kyutai 200 → 4.2). Both are small, tested, and live in the fork.
2. **Candle on this GPU is bound by per-op cost, not bandwidth.** The code predictor in Qwen runs
   15 sequential steps × 5 layers per frame and accounts for 60% of generation time; the Kyutai
   depformer runs 32 sequential steps per frame. llama.cpp is faster on Qwen; the likely reason
   is that it submits these loops as far fewer, larger command buffers (not verified here).
3. **Memory is a hard limit on this device.** About 8 GiB of device heaps: F32 weights for the
   1.6B/1.7B models do not fit, and with BF16 weights the 1.7B has too little headroom left for a GPU
   codec decode of ICL inputs (those decodes now run on a CPU decoder).
4. **Intelligibility was verified** (Whisper-tiny) for every row marked valid, which is what caught
   the Q8_0 failure. This checks content only, not naturalness or speaker similarity.

## 5. Recommended next steps (in order of expected payoff)

1. **Command-buffer batching in the Vulkan backend** (the fork's `perf/vulkan-experiments` branch
   has segmented submission and host-cost profiling; not on `feat/audio-runtime`). Targets the
   code predictor and depformer loops that dominate Qwen and Kyutai.
2. **Free GPU memory headroom**: the Vulkan backend keeps intermediate buffers alive until its queue is
   flushed, which is why chunking did not help; releasing them earlier (or flushing between layers)
   would let the codec and larger models stay on the GPU.
3. **Supertonic**: (tried and rejected: computing 1×1 convolutions as plain matmuls. It sped the vocoder up
   by ~20% but slowed the vector estimator's skinny `[2048,512]×[512,31]` products by a similar amount;
   whole-synthesis time was unchanged, 1448 ms vs 1450 ms, so it was reverted.) A native candle port of the four networks (or graph fusion) before any further
   Vulkan work; the interpreter is the bottleneck, not the GPU.
4. **Kyutai quality-preserving quantization** (e.g. keep activations/residual in F32, quantize only
   weights, or Q8 for the depformer only after validating with ASR).
5. Remaining gaps (everything else listed in section 2 is implemented and tested):
   * **The new default costs Supertonic speed and memory.** Default builds now include the candle
     features, so `model.backend = "auto"` runs Supertonic on candle: about 1.4–1.7× slower than ORT
     on this machine and 1.6 GiB instead of 0.5 GiB peak RSS (section 3.1). Set
     `model.backend = "ort"` (or `MODEL_BACKEND=ort`) to keep ONNX Runtime. I did not change the
     `auto` rule to prefer ORT because the goal was to make candle the engine.
   * Default builds now also need `slangc` (Slang shader compiler) for the Vulkan kernels, on top of
     the existing Vulkan SDK; CPU-only builds drop `candle-vulkan`.
   * Studio support for Kyutai covers model/voice selection and job synthesis; there is no
     dedicated per-voice management UI (voices are files in `voices_dir`).

### Decisions taken

* `model.backend = "auto"` stays on candle in builds that include it (the stated goal of the migration);
  operators who prefer ORT's speed and memory set `model.backend = "ort"`.
* No further Vulkan-submission work was requested; the Kyutai and Qwen numbers above are the shipped state.

## 8. Optimization round (Kyutai and Supertonic first)

Goal: implement the candle performance plan, starting with Kyutai and Supertonic; Qwen last.
Status: **round closed. Kyutai dispatches −59% (156,963 → 64,487), audio byte-identical to the reference path, RTF ≈ 2.0 (real time not reached). Supertonic unchanged at RTF 0.59–0.67. Final numbers in 8.2.**

What the measurements show (Vulkan, BC-250):

* **Time is dispatch-bound.** A dependent chain of tiny ops costs ~50 µs per op regardless of tensor
  size. Kyutai makes ~3500 dispatches per generated step (main LM ~1000, depformer ~2500), so the
  ~200 ms per step is almost entirely dispatch latency. A bf16 GEMV reaches ~120 GB/s, a quarter of peak,
  but GEMVs are only ~13 ms of the step.
* **Batching is not the bottleneck.** CPU encode is 0.7–0.8 s of each run; GPU wait is 84–97%.
  Overlapping submissions would save at most ~9% on Kyutai.
* **Host readbacks are not the main cost.** Kyutai has ~1000 readbacks (per-codebook sampling), but each
  one only costs a queue drain on top of the ~50 µs per dependent dispatch.
* **Supertonic dispatch sources** (vector estimator, 1 denoise step): Conv 898 (depthwise taps, ~15 per
  convolution), LayerNormalization 576 (~16 per node), Mul 487, Pad 316 (~11 per pad), Add 181.

Changes kept (verified: Supertonic parity denoise ≤3e-6, vocoder ≤3.4e-5; ONNX op tests unchanged):

| Change | Effect |
|---|---|
| Masks stay on the device when their inputs are on the device | host readbacks 140 → 105 |
| Scalar operands of Mul/Add/Sub/Div lowered to one affine dispatch | dispatches −1%; Supertonic RTF 0.93/0.80/0.72/0.77 → 0.85/0.72/0.70/0.74 |
| Dispatch counter (`Device::encode_count`) and per-op dispatch profile | tooling for the next steps |
| LayerNormalization (last axis, F32): centre the row, then the existing fused RMSNorm kernel | LayerNormalization dispatches 576 → 252 per denoise step; total dispatches 121,241 → 107,696 (−11%); parity unchanged (denoise ≤3e-6, vocoder ≤3.4e-5) |

Tried and reverted (measured, not kept):

* Kyutai: splitting the fused q/k/v and gate projections into separate matrices **increased** dispatches
  (156,963 → 170,259 per run) and did not change RTF.
* Supertonic: lowering 1×1 convolutions to matmul (see section 7): no gain.

Remaining dispatch sources in Supertonic (per denoise step, after LayerNorm): Conv 898 (depthwise taps), Mul 487,
Pad 316 (zero fills plus concatenation), Add 181. A native depthwise-conv kernel and a fused pad kernel are the
next Supertonic items; each is a new Slang shader plus Vulkan registration (about six places in
`candle-vulkan-kernels` and a backend method), not a composition change.

Next step that the measurements support: fused single-token kernels for Kyutai's attention and gated
MLP (one dispatch per block instead of ~30), and fused LayerNormalization, depthwise convolution and
padding kernels for Supertonic. These are new Slang kernels, not decompositions, and they are the only
path found that reduces the dispatch count substantially.

Kyutai is **not** real time (RTF 4.2–4.4 unchanged), so the target for this round was not met.

### 8.1 Fused kernels (second part of the round)

Implemented as single-dispatch Slang kernels in the fork (`candle-vulkan-kernels`, with Vulkan methods and
`Tensor` entry points in candle-core; each entry point declines and falls back to the composition when its
preconditions fail, and CPU builds get stubs):

| Kernel | Used by | Check against CPU reference |
|---|---|---|
| depthwise conv1d (F32) | Supertonic conv blocks | exact (max diff 0) |
| constant pad, up to 4 dims (F32) | Supertonic `Pad` | exact |
| single-query decode attention (bf16) | Kyutai self and cross attention | max diff 0.5–4e-3, bf16 output rounding |
| RMSNorm (bf16) | Kyutai norms | ASR-verified (same words); no f32 round trip |

Measured (same machine, same measurement method as above):

| | Before this round | After |
|---|---|---|
| Kyutai dispatches per run (short sentence) | 156,963 | 108,117 (−31%) |
| Kyutai RTF, short / medium sentence | 4.2–4.4 / n/a | 2.4 / 2.1 |
| Supertonic dispatches (4 syntheses) | 121,241 | 80,914 (−33%) |
| Supertonic RTF, short_en / medium / long / short_es | ~0.80 / 0.72 / 0.70 / 0.74 | 0.67 / 0.57 / 0.56 / 0.59 |

Verification: Supertonic parity (denoise ≤3e-6, vocoder 3.4e-5); Whisper-tiny reads back every Kyutai and
Supertonic output sentence used (short, medium, long, Spanish); candle-core conv tests 11/11; candle-onnx
op tests 70/71 (the known Gelu rounding test); default SonicBoom library suite 345/345.

Later in the same round: Kyutai's cross-attention LayerNorm takes a bf16 path (centre, then the fused RMSNorm,
then the bias). Dispatches on the short sentence fell from 108,117 to 100,197 (−7%); RTF stayed at 2.1–2.5
(within run-to-run noise), and the transcripts are unchanged. Dispatch count is not a reliable proxy for RTF
at this size: the remaining dispatches are individually cheap, so further small fusions do not move RTF
measurably.

Status against the plan: the fused attention, depthwise-conv, pad and bf16 RMSNorm kernels are implemented and
in use. **Kyutai is not real time (RTF ≈ 2.0); the real-time target is not met.** The fusions listed as next
steps were then implemented (8.2), except the depformer block fusion, which is still open.

Supertonic: per-op dispatch counts for one short run at five steps (`CANDLE_ONNX_PROFILE=1`, now printed by

Tried and rejected:

* Residual + RMSNorm + GEMV in one dispatch: slower (RTF ≈ 3.2 against 2.1 for the same build), and one
  in-model projection differed from the reference by one bf16 ULP on some rows, which changed the audio.
  The per-column recomputation of the row statistics is the likely cause of the slowdown.
* Depformer head split fused with the KV append: exact, but removes no dispatches (the split copies were
  already free views), so it was reverted.
* Pad fast path for strided (non-contiguous) inputs: no change in Pad count, and the output differed from the
  recorded wav; reverted before the difference was investigated.
* Q8_0 and Q4_0 quantized weights: Q8_0 fails ASR (section 3.2). Q4_0 was not validated.

Not done: the depformer block fusion (needs a whole-layer kernel, not yet designed), the segmented-submission
port from `perf/vulkan-experiments` (`c6e59c52`), and any Kyutai real-time target (about 2× would be needed).

Qwen3-TTS re-check at the end of the round (not part of the plan; 1.7B, Vulkan BF16, x-vector, 3 runs):
median RTF 5.63 (range 5.58–6.05), transcript "Hello, this is a native voice-cloning test." correct. The recorded
baseline in section 1 is 4.96 for the same configuration, so this is about 13% slower. The machine load average was
about 3 on 2 cores during the run, and an earlier run under load 8 gave RTF 9.4, so the gap is not attributed to
the fork changes without an A/B against the previous commit (not run).

## 6. Limits of this study

* One machine (2 cores, BC-250). RTF on other hardware will differ.
* Qwen/Kyutai: one sentence, one reference/voice, n = 1–3 per row. Supertonic: n = 5, four cases.
* The GGUF baseline row is from an earlier session; the llama.cpp build was not re-run here.
* Whisper-tiny is a coarse judge; no listening test, no speaker-similarity metric.
* RSS figures exclude GPU allocations.
* French was not exercised for Kyutai; Qwen only in English.
* Quantization and F16 failures are reported for these checkpoints only.

## 7. Reproduce

```sh
# Supertonic (ORT vs candle), results in benchmarks/results/<dir>
cargo build --release --example supertonic_backend_bench --no-default-features --features candle-vulkan
target/release/examples/supertonic_backend_bench parity models ort candle-vulkan 5
target/release/examples/supertonic_backend_bench bench candle-vulkan models 5 5 out/

# Qwen3-TTS (candle); dtype override QWEN3_TTS_DTYPE=f32|bf16
(cd vendor/qwen3-tts && cargo build --release --features cli,vulkan --example qwen_bench)
QWEN3_TTS_DTYPE=bf16 vendor/qwen3-tts/target/release/examples/qwen_bench \
  models/candle/qwen3-tts-1.7b-base vulkan ~/.cache/sb-models/ref-en.wav x_vector 3 clone_test out/

# Kyutai TTS (needs CXXFLAGS on GCC 14+ for the bundled SentencePiece sources)
(cd vendor/kyutai-tts && CXXFLAGS="-include cstdint" cargo build --release --features vulkan --example kyutai_bench)
K=models/candle/kyutai-tts; vendor/kyutai-tts/target/release/examples/kyutai_bench $K \
  $K/voices/ex03-ex01_calm_001_channel1_1143s.wav.1e68beda@240.safetensors vulkan bf16 2 short_en out/ 400

python3 scripts/summarize_candle_bench.py benchmarks/results/2026-11-15-candle
```
